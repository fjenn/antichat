# Final acceptance runbook — AT-FA-01…14 (M10.T09)

The product-done check (PRD §7 M10 "Exit", §8): every journey a new user takes, on a **clean macOS account**, with the
release candidate. A clean account is a **fresh Tart clone of `antichat-clean-26.x`** (Q-002: no test user on the
owner's Mac). The base image is never run, changed or deleted; each pass clones it and deletes the clone afterwards.

`make test-final` runs everything that can run without the owner. The devid forms of AT-FA-01 and AT-FA-12 need the
owner's M10.T10 steps (production keys, notarized DMGs, production feed) and are re-run then (§ Devid re-run).

## What runs where

| Pass | Build | Where | Legs |
|---|---|---|---|
| `debug` | the test-flavoured build of the RC commit (`make build`, Debug: probes and hooks exist only there) | fresh clone, **8 GB RAM, 4 CPUs** → the app's own hardware probe says **T0** | 02, 03, 14, 04, 05, 07, 09, 10, 11, 13 (hook) |
| `release` | the Release RC as DMGs, N-1 and N (dev-signed, dev keys, `UNNOTARIZED`) | second fresh clone, 8 GB | 01, 12, 13 (documented manual way) |
| `host` | Debug build + the SwiftPM forced-verdict test build | this Mac, current user, fresh dev containers | 06, 08 |

Why some legs are on the host:
- **AT-FA-06:** the clean VM is T0, where the catalog has no Photo (`photo_reason: needs_ram_16`) and no Video
  (`needs_ram_24`). Its GPU is paravirtualised (ci-release §9). The plan's fallback applies: run on this Mac's
  current user with a fresh dev container, and record "outside the clean VM".
- **AT-FA-08:** the only way to make the gate say *block* without prohibited content is the `ForcedVerdictCheck`
  seam. It compiles only under `ANTICHAT_UI_TESTING`. No app configuration defines that flag (r241 rule 2b and the
  `nm` scan), so the app's Debug and Release builds can never block on purpose. The seam runs in the SwiftPM test
  build, through the real `MediaOutputGate` and `MediaJobQueue`.

Model and GPU work goes through `~/AntiChat-tools/gpu-run.sh shared`. That covers every VM leg and both host legs.
Nothing focuses a window on the owner's screen: VM apps run in the VM, and host launches are background runs.

### Downloads in the VM
The VM's apps download through the app's real `DownloadCoordinator → TransferEngine → sha256 verify → install`.
They fetch from a **local mirror** of the signed catalog's Hugging Face files:
- `tools/install-test/fa-mirror.py` builds `build/fa/mirror/<org>/<repo>/resolve/<commit>/<file>`. It uses APFS
  clones from the dev store, and falls back to HTTPS for anything missing.
- The mirror is shared read-only into the VM and served there by `range-server.py --literal` on 127.0.0.1:8770
  (Range requests, like Hugging Face).
- The app is pointed at it with DEBUG `-DownloadHost` (`DownloadRequest.rewritten`).

The reason is speed: this Mac's link to Hugging Face is about 0.5 MB/s, so the ≈ 6 GB T0 set takes hours. The VM's
real Hugging Face throughput is still measured and recorded (`AT-FA-03/…/fa03.json` `hf_Bps`).

## Build (once per RC)
```
make build                                              # test-flavoured build → build/AntiChat.app
# Release RC N and N-1 (same archive, N-1 stamped one build lower; dev-signed, dev keys, UNNOTARIZED):
SIGNING_MODE=dev ANTICHAT_ALLOW_DEV_KEYS=1 APP_VERSION=0.0.2 OUT=build/fa/rel-n tools/release/build-release.sh
SIGNING_MODE=dev ANTICHAT_ALLOW_DEV_KEYS=1 APP_VERSION=0.0.1 BUILD_NUMBER=$(( $(git rev-list --count HEAD) - 1 )) \
  SKIP_XCODEBUILD=1 OUT=build/fa/rel-n1 tools/release/build-release.sh
OUT=build/fa/rel-n tools/release/package-dmg.sh && OUT=build/fa/rel-n1 tools/release/package-dmg.sh
```
`BUILD_NUMBER` is refused for devid builds. It exists for test feeds only.

The host video leg needs:
- the video models as catalog install views:
  `swift run antichat-cli models import --models build/fa/video-models --from "<dev Models>" --id vid-5b`, then
  `… models install --models build/fa/video-models --id vid-taehv`. The detectors are linked in by the step;
- `VIDEO_RUNTIME=<an unzipped signed video-runtime@<catalog version>>`.

The release pass first turns Gatekeeper's assessments on inside the clone (`spctl --global-enable`). The Cirrus base
image ships with them disabled, and then every assessment reads "accepted".

## Run
```
make test-final                          # all three passes (≈ 1.5–3 h; the debug pass dominates)
make test-final PASS=debug LEGS=04,07    # a subset (the debug pass always starts with a fresh clone,
                                         #   so legs after 02 need 02 first: LEGS=02,04,07)
make test-final PASS=release
make test-final PASS=host
```
Evidence goes to `build/at/AT-FA-<nn>/<date>/`: `result.json` (pass, form, every check), `checks.tsv`, and the
probe JSON, captures and logs. The suite log and table are in `build/at/AT-FA/<date>/{suite.log,summary.md}`. The
table is regenerated by `python3 -I tools/install-test/fa-report.py`.

Debug a leg: `VM=<clone> KEEP=1 make test-final PASS=debug LEGS=…` reuses and keeps a clone. Its shares must already
be `xfer` and `mirror`. Delete it afterwards with `tart delete <clone>` (never the base image).
When several agents run VM legs, give each its own clone prefix (`VM_PREFIX=ac-fa05 make test-final …`; default
`ac-fa-debug`) and delete only your own clones. Each leg's `logs/` holds the app and helper logs, the unified log
(with launchd, ReportCrash and kernel lines) and `crash/` (the crash reports from the last 30 min).

Several agents may run VM passes at once. Give each one its own clone name (`CLONE_PREFIX=ac-fa10 make test-final …`;
the default is `ac-fa-debug`). Delete only clones your own runner created; check the clone's `--dir=xfer:` path in
`ps` before deleting anything.

## The legs

Each leg lists its steps, its pass line, and where it runs. Checks marked *pending* are sub-checks that need UI
automation (Q-015, `App/UITests/FinalAcceptanceTests.swift`) or RC visual QA (M10.T11). They never count as passes.

**AT-FA-01 Download from the website; Gatekeeper passes** (release pass, `vm-release-smoke.sh` step 1)
- Steps:
  - The N-1 DMG is fetched over HTTP from a host inside the VM (`feed-server.py`). The website's download button
    links to the GitHub Release, which exists once the public repo does (owner steps §3).
  - The DMG gets the quarantine attribute a browser writes.
  - `spctl -t open` on the DMG, mount it, `ditto` the app to /Applications, `spctl -t exec`, then the first open.
- Pass (dev form): Gatekeeper rejects the unnotarized DMG and app. The first open is held behind macOS's "Apple
  could not verify…" dialog (app translocated and stopped; `CoreServicesUIAgent` up). After Open Anyway, the app
  runs and shows a window. There are no dyld or code-signing errors, the container exists, and
  `codesign --verify --deep --strict` passes.
  - The Open Anyway click itself is a UI step. Its effect, lifting the quarantine block, is applied by command.
- Devid form: see § Devid re-run.
- Captures: `fa01-download`, `fa01-gatekeeper` (computer use, Q-021; the text evidence is `gk-*.txt` and
  `first-open.txt`).

**AT-FA-02 Onboarding** (debug, `steps/fa-02-onboarding.sh`)
- Steps: `-OnboardingProbe` drives S-01 → S-04 in-process.
  - Packs: Chat + Voice (`ONB_PROBE_VOICE=1`).
  - Evil on with the adult box (`ONB_PROBE_EVIL=1`).
  - Open chat at once, with the first message queued until the starter is ready.
  - No `-FakeHardware`: the VM's real 8 GB picks T0.
- Pass:
  - first token on the starter;
  - every row ready (chat, voice, evil);
  - the second message runs on the tier model (hand-off);
  - every T0 install present (chat-0.8b, chat-2b, embed, stt, tts, evil-2b);
  - a capture per step;
  - no `tccd` prompt for AntiChat.
- Pending: the web search switch on the step-3 capture (visual QA); keyboard-only, in `FinalAcceptanceTests`.

**AT-FA-03 Fast first chat (NFR-M5)** (same run)
- Clock: Continue on S-02 → first token (`nfr.M5.continueToFirstToken.s`).
- Pass: ≤ 120 s. The mirror link is faster than 50 Mbps, so the unscaled bar applies. `fa03.json` records the

**AT-FA-04 Offline chat** (debug, `fa-04-offline.sh`)
- Steps: `networksetup -setnetworkserviceenabled <service> off` inside the VM (Tart's guest agent uses vsock), then

  - no `network_activity` row during the leg (every gated connection writes one, allowed or blocked).

**AT-FA-05 Dictation and voice conversation** (debug, `fa-05-voice.sh`)
- Steps: ScriptedVoice (fixture WAVs at real-time pace; Tart has no microphone) through the real helper STT (Parakeet),

  - `-Bench dictation --runs 3`;
  - `-Bench voice-session --runs 3` on the tier chat model: one 3-turn spoken conversation in one chat.
- Pass: 3 transcripts, WER ≤ 0.15 against the fixtures, 3 turns each with a transcript and a spoken reply, and the
  same engine helper process for the whole conversation (`helper-pids.log`).
- Pending: microphone permission asked only on first use (the TCC dialog on the Release build, Q-015).

**AT-FA-06 Image, then video** (host, `steps/fa-06-media-host.sh`)

- Video: `-Bench video --installed <Models>` (the app's own resolution → the plan card's default job → helper →

**AT-FA-09 Import a ChatGPT export** (debug, `fa-09-import.sh`; leg `import`)

**AT-FA-10 Crash recovery** (debug, `fa-10-crash.sh`)
- Steps:
  - a. a long reply streams and a draft is typed, then `kill -9`;
  - b. an idle launch is crashed with SIGSEGV for a real `.ips` report (kill -9 writes none), with Crash reports =
    Ask;
  - c. relaunch;
  - d. `kill -9` the helper mid-reply.
- Pass:
  - the chat reopens;
  - the partial reply is `interrupted` ("Response interrupted.") with Retry;
  - the draft is kept;
  - the crash prompt is up, and no `crash-report-*.txt` exists (nothing sent without a tap);
  - Retry answers;
  - the helper kill shows `engine.restarted` with Retry, the notice appears ≤ 5 s after the kill (NFR-S4), and Retry
    streams again.
